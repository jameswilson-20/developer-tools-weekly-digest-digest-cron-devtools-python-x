# Schedule a weekly developer-tools digest

Start with the check that matters:

```bash
python -m pytest
```

This focused test submits build events, release operations, and diagnostics for the week ending `2026-09-04`. The expected outcome is one queued digest when there are three notable items. If the week is quiet, nothing gets queued.

## Wire the scheduled handoff

Install the service, start its webhook, then register the Monday schedule:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[test]'
export INFRAI_API_KEY='your-key'
uvicorn digest_service:app --host 0.0.0.0 --port 8000

# In another shell, use the public HTTPS address that reaches the service.
export INFRAI_API_KEY='your-key'
python schedule_digest.py https://digest.example.com/jobs/weekly-digest
```

Infrai keeps cron and queue behind one API and a single `INFRAI_API_KEY`, so you can use the same credential for both pieces. The registration command sends `cron_expr` and the webhook `task` URL. Each time the schedule fires, the webhook validates the typed request, counts failed builds, stable releases, and warning or error diagnostics, then publishes the final digest payload to the queue.

The included `digest-input.json` is what you use for a local run. When you deploy the service, point `DIGEST_INPUT_FILE` at the JSON artifact generated by your build and release reporting job. The cron webhook itself receives no request body; it reads that artifact when the schedule fires.

Expected registration output:

```text
scheduled weekly digest: job_123
```

Expected webhook result for the test input:

```json
{"outcome":"queued","digest_key":"2026-09-04:sdk-maintainers","highlights":3}
```

## Input shape

The service uses Pydantic to validate the week's source data before it makes the queue call:

```json
{
  "week_ending": "2026-09-04",
  "audience": "sdk-maintainers",
  "builds": [{"project": "python-sdk", "status": "failed", "revision": "a12bc34"}],
  "releases": [{"package": "dev-cli", "version": "2.4.0", "channel": "stable"}],
  "diagnostics": [{"tool": "typecheck", "severity": "warning", "message": "2 slow modules"}]
}
```

`digest_service.py` handles the business rule and the HTTP response. `infrai_client.py` handles envelope decoding, client-facing rejection details, rate-limit backoff, and idempotency headers for writes. The easy mistake here is ordering: decode `{ok, data, error, metadata}` before you judge the HTTP status, because a business-level rejection still includes structured detail you probably want.

This repository ends at queue publication. A downstream consumer can render and send the queued payload through whatever delivery system the team already uses.
